# Use environment-specific PostgreSQL databases

GTD on Rails will replace its synchronized SQLite database with PostgreSQL while keeping the local Spring Boot sidecar as the only database client. The sidecar will connect through JDBC to independent Supabase projects for production and staging, while development will use a local PostgreSQL container. Production and staging Database Connection Configuration will live in profile-specific `database.properties` files synchronized by rclone, use a dedicated non-administrative database role, and be restricted to the local owner with mode `0600`. Containers are limited to development database infrastructure; Tauri and the sidecar remain native host processes so they retain direct access to Wayland, desktop integrations, and local asset paths. Rclone becomes File Sync for assets and trusted local configuration; it no longer transports the database or runs after mutations that only change structured data. This isolates structured persistence from rclone because synchronizing a live SQLite file proved conflict-prone while independently stored files remain suitable for file synchronization.

Existing production data will move through a one-time offline cutover command included in the native distribution and run only on the primary computer while both desktop installations are closed. The command will synchronize files, preserve the SQLite database as a backup, initialize PostgreSQL, import and validate the existing records, and refuse an unsafe or repeated migration. The second computer will connect to the already migrated shared database without importing its local SQLite copy.

The production database records cutover state as `AWAITING_LEGACY_IMPORT`, `IMPORTING`, `READY`, or `FAILED`. Database Setup marks a provisioned production schema awaiting import when it finds legacy SQLite data, and normal application startup remains blocked until validated import atomically reaches `READY`. Failed or partial attempts preserve the SQLite source and can be retried safely; a genuinely new production database requires explicit confirmation before starting directly as `READY`.

Rollback to the preserved SQLite database is allowed only before normal PostgreSQL use begins. Once a `READY` production database receives new application writes, SQLite becomes historical recovery material and all operational recovery remains PostgreSQL-to-PostgreSQL through fixes or logical dump restoration; the project does not implement reverse migration or dual-write.

Production and staging use independent Supabase projects rather than databases or schemas sharing one project. Their JDBC traffic will use each project's Supavisor session pooler on port 5432. Session mode preserves persistent backend connection semantics while avoiding a dependency on IPv6 connectivity; transaction mode is excluded because this is a long-lived sidecar rather than a serverless client.

Each environment stores application objects in a dedicated `gtd` schema owned by its application database role. The role may migrate and operate that schema but has no administrative access to the Supabase project or unrelated schemas such as `auth` and `storage`; JDBC and Flyway use `gtd` as their default schema.

Remote JDBC connections require TLS with full certificate and hostname verification. Each Supabase environment keeps its public database CA certificate beside its synchronized Database Connection Configuration; missing or invalid trust material prevents startup. Local development PostgreSQL remains accessible only through localhost and does not require TLS.

Database availability becomes part of application readiness because structured data has no local fallback. The sidecar will verify PostgreSQL connectivity, report connectivity failures as `503 Service Unavailable`, and the desktop will block normal interaction while readiness is failing, then recover through polling when the database becomes available again.

Runtime database loss immediately blocks the whole desktop. This migration deliberately adds no offline mutation queue, special draft preservation, or automatic mutation replay; recent unpersisted edits may be lost. When readiness recovers, the desktop reloads application state from PostgreSQL before restoring interaction.

All automated validation that requires persistence will use isolated PostgreSQL databases managed by a disposable test Compose lifecycle under `pnpm test`. SQLite and in-memory substitutes are excluded from integration and end-to-end tests so schema migrations, UUID mappings, constraints, and transaction behavior match the production database engine. The persistent development database remains separate from all test databases.

PostgreSQL starts with a new Flyway `V1` baseline that describes the current schema instead of replaying SQLite history. Legacy SQLite migrations leave the active runtime; a final-schema test fixture and the temporary SQLite reader used by the cutover command provide the compatibility needed to verify import behavior. Git history remains the archive for the removed SQLite migrations.

Runtime file roots are isolated by environment. Production keeps `~/Documents/gtd-on-rails`; staging and development use Git-ignored `staging-gtd-on-rails` and `dev-gtd-on-rails` directories under the repository root. Staging has its own rclone remote, while development keeps file-backed state local and disables rclone by default.

Development Compose starts automatically for `pnpm dev` and preserves its PostgreSQL volume and local assets across runs. The explicit `pnpm dev:reset` workflow requires the `DEVELOPMENT` database identity, recreates the local database and asset dataset, seeds fake data, and then starts development.

Staging contains only disposable fake data and never clones production automatically. A normal `pnpm staging` run preserves and opens the existing staging dataset. The explicit `pnpm staging:reset` workflow resets the staging database and seeds a deterministic test dataset before opening the desktop. Destructive database operations require both the staging runtime profile and a persistent `STAGING` identity stored in the target database; a mismatch fails without changing data. Production, development, and test databases carry distinct identities.

The explicit staging reset treats database rows and assets as one disposable dataset. It preserves profile-specific configuration files and the rclone marker, removes database-backed Google authorization, recreates database content and the staging asset directory, then completes a blocking File Sync before the desktop becomes ready. Normal staging startup does none of these destructive steps.

Only one trusted desktop installation is active at a time. Before switching computers, the owner waits for File Sync to complete successfully on the active installation; the next installation completes blocking startup File Sync before connecting to PostgreSQL and exposing database-backed asset metadata. This operational invariant replaces distributed leases, concurrent-edit reconciliation, and automatic missing-asset recovery.

On packaged desktop startup, native release update checking and installation occur before the database sidecar starts. The sidecar also verifies that its supported Flyway schema version is compatible with the shared database; an older installation facing a newer schema remains blocked with an update-required state rather than accessing the database. This check remains the fail-safe when release checking or installation is unavailable.

Because the Supabase Free Plan does not provide user-restorable automatic backups, production creates application-owned logical dumps of the `gtd` schema before Flyway upgrades and at most once per active day. It retains 30 daily backups under the production file root and distributes the closed dump files through File Sync. Restore validation targets staging; overwriting production requires a separate explicit recovery action.

Production installations depend on the Arch Linux `postgresql-libs` package for `pg_dump` and `pg_restore`. Startup verifies the tools before starting the sidecar; when absent, the graphical desktop may offer an explicit fixed-argument `pkexec pacman -S --needed --noconfirm postgresql-libs` action backed by Polkit authentication, with cancellation and manual-command fallback. The application never performs silent package installation.

The application stores no Supabase Management API token and does not attempt to resume paused Free Plan projects. Database readiness reports the unavailable project, and the owner resumes it manually through the Supabase dashboard before retrying startup.

After successful startup File Sync, an absent `database.properties` enters Database Setup instead of failing normal startup. The setup accepts a Supabase administrative connection in memory, validates the remote environment over TLS, provisions the `gtd` schema and a randomly credentialed application role, writes only the limited Database Connection Configuration with mode `0600`, publishes it through File Sync, discards the administrative credential, and restarts the sidecar normally. Production legacy data still requires the separate explicit cutover command.

Packaged production and staging start an updated temporary Java bootstrap sidecar without JPA, Flyway, or GTD domain endpoints. It owns startup File Sync and Database Setup or repair, exits after producing a valid configuration, and is replaced by the normal database-backed sidecar. Development uses its known local Docker connection and skips remote database bootstrap; database provisioning and secret handling are not duplicated in the Rust shell.

An existing but unusable Database Connection Configuration never falls back to first-time setup. Startup preserves the file and exposes retry or an explicit repair flow; repair requires a fresh in-memory administrative connection, validates the database identity, rotates the limited application credential, and replaces the file only after successful verification. Environment identity mismatches fail without repair.
